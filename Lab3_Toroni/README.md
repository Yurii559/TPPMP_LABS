## Детальний розбір реалізації

### Завдання №1 — Робота з пам'яттю

У першому завданні на прикладі класів із логуванням в `init` та `deinit` досліджено, як ARC звільняє об'єкти з пам'яті:

* **Глобальний vs локальний scope:** об'єкт `globalPerson` живе до завершення роботи програми, тому його `deinit` не викликається під час виконання. Натомість об'єкт `localPerson`, створений усередині блоку `do {}`, знищується одразу після виходу з цієї області видимості (лічильник посилань падає до `0`).
* **Проблема (`PersonLeaky` та `SonLeaky`):** батьківський об'єкт тримає сильне посилання `child` на сина, а син — сильне посилання `parent` на батька. Після виходу з `do {}` лічильник посилань кожного об'єкта зменшується з `2` до `1`, але не до `0` — виникає витік пам'яті (*Memory Leak*), і `deinit` не викликається.
* **Вирішення (`PersonFixed` та `SonFixed`):** зворотне посилання в дочірньому класі оголошено як `weak var parent: PersonFixed?`. Слабке посилання не збільшує *retain count*, тому після виходу з блоку обидва об'єкти коректно видаляються з пам'яті.

```swift
class SonFixed {
    let name: String
    weak var parent: PersonFixed? 
}
```

### Завдання №2 — Цикли сильних посилань у замиканнях

Замикання (*closures*) у Swift є посилальними типами, тому збереження замикання у властивості об'єкта, яке водночас захоплює цей самий об'єкт, створює замкнений цикл. Завдання розділене на дві частини:

* **Частина 1 (`Operand`):** замикання `sumClosure` зберігається в об'єкті `op1` і обчислює суму `op1.number + op1.operand?.number`. Без списку захоплення створюється цикл `op1 → sumClosure → op1`, через що в пам'яті зависають одразу два об'єкти (`op1` та `op2`). Додавання `[weak op1]` із безпечним розгортанням через `guard let` повністю усуває витік.
* **Частина 2 (`OperandBlockLeaky` та `OperandBlockFixed`):** замикання `aBlock` ініціалізується й викликається прямо в `init()`. При заніленні (`leakyObj = nil`) об'єкт із сильним захопленням `self` залишається в пам'яті. У виправленому класі використано `[weak self]` та опціональний ланцюжок `self?.aConstant`, завдяки чому `deinit` спрацьовує миттєво після присвоєння `nil`.

```swift
op1.sumClosure = { [weak op1] in
    guard let op1 = op1 else { return 0 }
    return op1.number + (op1.operand?.number ?? 0)
}
```

### Завдання №3 — Ручне управління пам'яттю (MMR) в Objective-C

У цьому завданні ARC вимкнено (`-fno-objc-arc`), тому відповідальність за підрахунок посилань лежить на розробнику. Реалізовано клас `MyNumber` із властивістю `@property (nonatomic, retain) NSNumber *value` та перевизначеним методом `dealloc`, який звільняє внутрішній об'єкт `[_value release]` перед викликом `[super dealloc]`.

Продемонстровано два способи звільнення пам'яті:

1. **Пряме звільнення (`alloc` / `release`):** після роботи з `num1` викликається `[num1 release]`, що обнуляє `retainCount` і миттєво запускає `dealloc`.
2. **Відкладене звільнення (`NSAutoreleasePool` / `autorelease`):** об'єкт `num2` позначається як `autorelease` усередині `innerPool`. Коли пул звільняється (`[innerPool release]`), він автоматично надсилає `release` усім доданим до нього об'єктам.

```objc
- (void)dealloc {
    NSLog(@"MyNumber dealloc (value = %@)", _value);
    [_value release];
    [super dealloc];
}
```

### Завдання №4 — Усунення витоку пам'яті через `unowned`

Згідно з правилами управління пам'яттю Apple, батьківський об'єкт має володіти дочірнім (сильне посилання), але не навпаки. У моделі `Contact` — `Number` номер телефону не може існувати без контакту, тому замість сильного посилання у класі `Number` використано модифікатор `unowned`:

```swift
class Number {
    let digits: String
    unowned var contact: Contact 
    // ...
}
```

На відміну від `weak`, посилання `unowned` не є опціональним і гарантує, що об'єкт `Contact` завжди існує, доки існує прив'язаний до нього `Number`. При видаленні контакту обидва об'єкти коректно знищуються без витоків пам'яті.
